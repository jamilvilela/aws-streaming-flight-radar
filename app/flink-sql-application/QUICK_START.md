-- ============================================================================
-- GUIA RÁPIDO: ARQUITETURA SQL FLINK + REDSHIFT
-- ============================================================================
--
-- Este guia explica como usar Flink SQL ao invés de Java para:
-- • Ingerir dados ADS-B do Kinesis
-- • Enriquecer com conversões de unidades
-- • Criar 4 sinks para diferentes casos de uso
-- • Integrar com Redshift e QuickSight
--
-- ============================================================================
-- 1. POR QUE FLINK SQL AO INVÉS DE JAVA?
-- ============================================================================
--
-- ✓ Flink SQL:
--   • Mais simples e legível
--   • Sem compilação/deploy de JAR
--   • Ideal para transformações declarativas
--   • Suporte nativo a TUMBLE, HOP windows
--   • Integração direta com Kinesis + Redshift
--
-- ✗ Flink Java:
--   • Mais verbose (DataStream API)
--   • Requer compilação + upload JAR
--   • Bom para lógica complexa e stateful
--
-- ============================================================================
-- 2. ARQUITETURA DE 3 CAMADAS
-- ============================================================================
--
-- CAMADA 1: INGESTÃO (01_source.sql)
-- ┌────────────────────────────────────────────────────┐
-- │ CREATE TABLE state_vectors_source                 │
-- │ ├─ Fonte: Kinesis "flights-raw"                   │
-- │ ├─ Formato: JSON                                  │
-- │ ├─ Metadados: event_time (timestamp Kinesis)      │
-- │ └─ Watermark: 30s (tolera atrasos)               │
-- └────────────────────────────────────────────────────┘
--
-- CAMADA 2: TRANSFORMAÇÃO (02_enriched_view.sql)
-- ┌────────────────────────────────────────────────────┐
-- │ CREATE TEMPORARY VIEW enriched_flights            │
-- │ ├─ Conversão de unidades (m/s→kts, m→ft)         │
-- │ ├─ Classificações:                                │
-- │ │  ├─ flight_phase (ground, takeoff_landing,...)  │
-- │ │  ├─ vertical_trend (climbing, descending,...)   │
-- │ │  └─ speed_category (slow, medium, fast,...)     │
-- │ └─ Validações: coordenadas, icao24               │
-- └────────────────────────────────────────────────────┘
--
-- CAMADA 3: SINKS (03_sinks_kinesis.sql)
-- ┌────────────────────────────────────────────────────────────────┐
-- │ Sink A: kinesis_positions_1min                                │
-- │ └─ Agregação: país + fase, TUMBLE(1 min), 100-300 evt/min    │
-- │                                                               │
-- │ Sink B: kinesis_altitude_bands                               │
-- │ └─ Agregação: fase + tendência, TUMBLE(1 min), 500k-1k evt  │
-- │                                                               │
-- │ Sink C: kinesis_phase_changes                                │
-- │ └─ Filtrado: mudanças > 500 fpm, TUMBLE(30s), 100-500 evt   │
-- │                                                               │
-- │ Sink D: kinesis_enriched_raw                                 │
-- │ └─ Passthrough enriquecido, ~50k-100k evt/min                │
-- └────────────────────────────────────────────────────────────────┘
--
-- ============================================================================
-- 3. ORDEM DE EXECUÇÃO
-- ============================================================================
--
-- 1. Execute 01_source.sql (cria tabela SOURCE)
-- 2. Execute 02_enriched_view.sql (cria VIEW com transformações)
-- 3. Execute 03_sinks_kinesis.sql (cria sinks + INSERT INTO)
--
-- Notas:
--   • A VIEW enriched_flights depende de state_vectors_source
--   • Os sinks (INSERT INTO) consomem da VIEW enriched_flights
--   • Após executar, Flink começa a processar automaticamente
--
-- ============================================================================
-- 4. FLUXO DE DADOS: EXEMPLO PASSO-A-PASSO
-- ============================================================================
--
-- [INPUT] OpenSky API → Lambda → Kinesis (flights-raw)
-- ─────────────────────────────────────────────────────
-- Evento JSON bruto:
-- {
--   "icao24": "a02345",
--   "callsign": "TAP1234",
--   "origin_country": "PT",
--   "altitude": 3500,           ← em METROS
--   "velocity": 250.5,          ← em M/S
--   "vertical_rate": 5.2,       ← em M/S (positivo=subindo)
--   "on_ground": false,
--   "longitude": -9.1352,
--   "latitude": 38.6814
-- }
--
-- [ENRIQUECIMENTO] enriched_flights VIEW
-- ────────────────────────────────────────
-- SELECT
--   altitude_ft = 3500 * 3.28084 = 11,483 ft
--   velocity_kts = 250.5 * 1.94384 = 486.5 kts
--   vrate_fpm = 5.2 * 196.85 = 1024 fpm
--   flight_phase = CASE WHEN 11483 < 35000 THEN 'cruise' END
--   vertical_trend = CASE WHEN 5.2 > 2.0 THEN 'climbing' END
--   speed_category = CASE WHEN 486.5 BETWEEN 300 AND 500 THEN 'fast' END
--
-- [SINKS] Processamento paralelo em 4 destinos
-- ──────────────────────────────────────────────
-- 
-- Sink A (positions-1min):
--   TUMBLE_START = 14:30:00
--   origin_country = PT
--   flight_phase = cruise
--   aircraft_count = 1 (apenas essa aeronave nessa janela)
--   avg_altitude_ft = 11483
--   avg_velocity_kts = 486.5
--   OUTPUT: {"window_start": "14:30:00", "origin_country": "PT", ...}
--
-- Sink B (altitude-bands):
--   TUMBLE_START = 14:30:00
--   flight_phase = cruise
--   vertical_trend = climbing
--   aircraft_count = 1
--   avg_altitude_ft = 11483
--   OUTPUT: {"window_start": "14:30:00", "flight_phase": "cruise", ...}
--
-- Sink C (phase-changes):
--   TUMBLE_START = 14:30:00
--   icao24 = a02345
--   callsign = TAP1234
--   vrate_fpm = 1024 (> 500, então INCLUÍDO)
--   altitude_ft = 11483
--   OUTPUT: evento completo com mudança de fase
--
-- Sink D (enriched-raw):
--   icao24 = a02345
--   callsign = TAP1234
--   longitude = -9.1352
--   latitude = 38.6814
--   altitude_ft = 11483
--   velocity_kts = 486.5
--   flight_phase = cruise
--   vertical_trend = climbing
--   speed_category = fast
--   OUTPUT: evento enriquecido completo para histórico
--
-- ============================================================================
-- 5. INTEGRAÇÃO COM REDSHIFT
-- ============================================================================
--
-- Arquivo: redshift_schema.sql
--
-- Fluxo:
--   Kinesis Streams → (Firehose) → S3 → Redshift COPY
--                      ↓
--                   (ou direto via External Schema)
--
-- MVs em Redshift (auto-refresh a cada 10s):
--   • mv_positions_1min → heatmap de tráfego
--   • mv_altitude_bands → distribuição por altitude
--   • mv_phase_changes → alertas de mudanças
--
-- Fact Tables:
--   • fact_flight_positions → histórico 1min agregado
--   • fact_altitude_bands → histórico distribuição altitude
--   • fact_enriched_flights → histórico completo (todas aeronaves)
--
-- ============================================================================
-- 6. DASHBOARDS QUICKSIGHT
-- ============================================================================
--
-- Dataset 1: Real-time (Redshift MVs - atualiza 10s)
--   • Mapas de heatmap (origem_country, flight_phase)
--   • Gauges de tráfego global
--   • Alertas de eventos críticos
--
-- Dataset 2: Histórico (Redshift Fact Tables)
--   • Análise de tendências (última semana/mês)
--   • Comparação horária/diária
--   • Anomalias detectadas
--
-- Dataset 3: Data Science (Spark/EMR)
--   • fact_enriched_flights → clustering de rotas
--   • Análise de padrões de heading por região
--   • Detecção de anomalias comportamentais
--
-- ============================================================================
-- 7. MONITORAMENTO E ALERTAS
-- ============================================================================
--
-- CloudWatch Logs:
--   /aws/kinesisanalytics/flight-radar-kda-flights
--   └─ FlinkApplicationLogs
--
-- Métricas a monitorar:
--   • Input records/second (flights-raw)
--   • Output records/second (sinks A-D)
--   • Event time latency
--   • Checkpoint duration
--
-- Alertas recomendados:
--   1. Input stream vazio > 5 min (problema na API?)
--   2. Output Sink D < input (dados perdidos?)
--   3. Checkpoint failure (problema no estado?)
--   4. Downtime da aplicação (OOM, crash?)
--
-- ============================================================================
-- 8. PERFORMANCE E CUSTOS
-- ============================================================================
--
-- DPU (Data Processing Unit) na KDA:
--   • 1 DPU = 1 parallelism + 4GB memory
--   • Throughput: ~100k eventos/min por DPU
--   • Custo: $0.50/hora por DPU
--
-- Estimativa para 100k evt/min:
--   • Parallelism: 4 (4 DPUs necessárias)
--   • Custo: ~$48/dia
--   • Auto-scaling pode aumentar conforme demanda
--
-- Otimizações:
--   • Usar TUMBLE windows ao invés de SESSION (mais determinístico)
--   • Filtrar dados cedo (WHERE no source, não no sink)
--   • Particionar sinks por origem_country (melhor throughput)
--
-- ============================================================================
-- 9. TROUBLESHOOTING
-- ============================================================================
--
-- Problema: Nenhum evento no sink
-- Solução:
--   1. Verificar se stream flights-raw tem dados
--   2. Conferir permissões IAM (read Kinesis, write CloudWatch Logs)
--   3. Ver logs de erro no CloudWatch
--   4. Testar com dados manualmente: aws kinesis put-record ...
--
-- Problema: Sink outputs muito baixo comparado ao input
-- Solução:
--   1. Aumentar parallelism (mais DPUs)
--   2. Verificar se há backpressure nos sinks (Kinesis full?)
--   3. Reduzir agregação window (não fazer TUMBLE(1min) em algo que
--      muda 10x por segundo)
--
-- Problema: Sink D tem lag (enriquecimento atrasado)
-- Solução:
--   1. Este é o sink de "passthrough", deve ser rápido
--   2. Aumentar parallelism.per_kpu em flink_application_configuration
--   3. Verificar se há JVM GC pauses (logs)
--
